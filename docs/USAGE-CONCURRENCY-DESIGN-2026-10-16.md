# 中转站客户端优化设计

日期：2026-10-16  
状态：已在本地实现，待实机性能采样和发布
优先级：斗地主性能 P0；使用记录、管理员并发管理 P1

## 目标

这次优化解决三个相互独立但都需要同一套数据边界的问题：

1. 斗地主进入和对局过程恢复到可玩状态，点击出牌不能被渲染或特效拖住。
2. 用户可以查看自己的请求级使用记录，而不是只能看到聚合用量。
3. 管理员可以按当前并发管理用户，默认把最繁忙的用户排在前面，并能进入用户详情。

本稿描述交互、性能、数据和验收标准。当前没有运行时 FPS/CPU 采样，因此斗地主的根因仍是“源码证据支持的高概率原因”，本地实现后仍要用诊断开关补一次真实牌局采样。这里的“使用记录”默认指中转 API 请求记录；斗地主对局记录要单独定义，不能和 API Token 用量混在一张表里。

## P0：斗地主性能专项

### 当前渲染链路和高概率卡点

- `src/useDdz.ts:27-61` 收到每一条 WebSocket 桌面快照就调用 `setTable`。快照即使只改变倒计时或一个状态，也会让整棵 `DdzView` 子树重新计算。
- `src/components/DdzView.tsx:379-416` 的牌桌把顶部、三个座位、中央出牌区、手牌、操作区、结算层和 Canvas 特效放在同一棵树中；`TableScene` 目前接收完整 `table` 对象。
- `src/components/DdzView.tsx:607-616` 每个头像都调用 `useCountdown`；`src/components/DdzView.tsx:1187-1191` 每个倒计时每 250ms 触发一次 React 更新。没有活动回合时，这些定时器仍然运行。
- `src/components/DdzView.tsx:1126-1175` 在炸弹/火箭上启动 Canvas 粒子、页面抖动和横幅；`src/components/fx.ts` 的单次粒子数为 90/140。
- `src/index.css:6075-6112` 和牌桌附近样式使用多层渐变、阴影、滤镜、遮罩和太阳纹。低性能设备上，合成层和绘制成本可能比 React 本身更高。
- 进入链路还会重复请求状态：`App.tsx` 会预取 `ddz_status`，`DdzView` 挂载后每 15 秒刷新一次，`enter()` 再请求一次；`useDdz` 同时立即建立 WebSocket。Rust 端 attach 还会同步处理用户/在线状态/首个快照，这些耗时要和前端绘制分开量。

这些点解释了“进入卡一下”和“整局卡”的共同表现，但还不能单凭静态代码断言唯一根因。第一版改造必须保留快照序号和动作语义，只改变前端显示调度。

### 实测结论（2026-10-16，Safari 27 / WebKit）

用生产构建加 `SimTable` 模拟牌局（机器人每 400ms 出一手，1920×914 @2x）逐项二分，帧数只统计窗口可见的时间：

| 状态 | 平均帧率 | 每帧中位数 | 6 秒内超过 50ms 的帧 |
| --- | --- | --- | --- |
| 原标准模式 | 13.7 fps | 69ms | 72 |
| 修复后标准模式 | 30–36 fps | 17ms | 32–35 |
| 牌桌全部动画关闭（理论上限） | 43 fps | 17ms | 19 |

- 每个快照的 JS 加布局只要 2–5ms，WebSocket 合帧和倒计时改动不是主要收益来源；瓶颈在 WebKit 绘制。
- 主因是持续动画落在无法合成的元素上：当前出牌者的英雄徽章带 `drop-shadow` 和八角形 `clip-path`，又一直做 `ddz-breathe` 缩放；技能按钮的 `ddz-skill-glow` 一直在改 30px 模糊的 `box-shadow`。两者每帧都要重新光栅化。
- 其次是每手牌的飞入动画（`ddz-from-*`），每次都新建一层带阴影的卡牌：关闭后从 26 fps 升到 40 fps。
- 标准模式因此去掉了徽章滤镜、呼吸缩放、技能光晕、出牌飞入和秒数跳动，翻底牌改为只用 transform；高质量模式保持原效果。
- 剩余的长帧大约每个快照一次，全关动画时也存在。最初怀疑是牌桌大面积渐变的重绘，后续二分推翻了这个判断，见下文。

#### 剩余长帧的根因（第二轮，同日）

同样的生产构建和 `SimTable`（400ms 一手，1699×875 @2x），每项至少 6 秒可见时间：

| 状态 | 平均帧率 | 每帧中位数 | 6 秒内超过 50ms 的帧 |
| --- | --- | --- | --- |
| 直接进牌桌，不经过大厅 | 60 fps | 17ms | 0 |
| 先显示大厅再进牌桌（v0.9.7） | 36–43 fps | 17ms | 18–32 |
| 先显示大厅再进牌桌，徽章改用 `box-shadow`（本次） | 60 fps | 17ms | 0（连续 30 秒，包含结算和技能横幅） |

- 长帧和牌桌本身无关：隐藏手牌或中央区、去掉装饰、把牌桌提成独立合成层（`will-change`）、拿掉 aurora 背景，都没有改善。
- 触发条件是**同一个 WebKit 进程里画过一次带 `filter: drop-shadow` 的英雄徽章**。徽章的结构是父元素加滤镜，伪元素和表面再各自 `clip-path` 成八角形。大厅英雄区的 9 个徽章、技能横幅里的大徽章都属于这种情况。画过之后，之后每个快照都会有约 2 个 ~100ms 的帧，换页面后仍然存在：同一标签导航到不经过大厅的页面也照样慢，新开标签才恢复。
- 逐项排除：标题的 `background-clip: text` 渐变字不触发；隐藏徽章里的 Logo 仍然触发；只去掉徽章的 `filter` 就不再触发。牌桌上的 `.ddz-mult`、`.btn-gold` 也有 `drop-shadow`，但滤镜和 `clip-path` 在同一个元素上，不触发。
- 修复只改 `.ddz-standard`：徽章不再用 `filter`，改为 `border-radius: 50%` 的圆形 `box-shadow` 垫在八角形下面，地主再加一圈金色外光。截图对比与原来的投影基本一致。高质量模式保留原来的滤镜，预计仍有这个问题，但没有单独测。
- 测量注意：Safari 同源标签共享 WebContent 进程，后台标签里还在跑的模拟牌局也会拖慢前台。另外进程一旦进入慢状态就会一直保持。所以每个配置都要在新开的单个标签里测。上一轮的测试页先渲染了大厅，所以测到的"剩余长帧"其实就是这个问题。

### 用户可感知的目标状态

- 进入斗地主后先看到可点击的牌桌/大厅骨架；本地缓存或无网络资源时 p95 ≤ 200ms，常规设备 p95 ≤ 500ms。连接在后台建立，连接状态以轻量提示覆盖，不阻塞页面首次绘制。
- WebSocket 建连后首个可操作状态在 1 秒内出现；点击出牌到按钮反馈不超过 100ms，网络确认不改变本地按钮的即时反馈。
- 正常回合在目标设备上保持接近 60 FPS；普通状态不启动粒子 Canvas，不因倒计时每 250ms 重绘整张牌桌。
- 合并快照只影响视觉更新，不能丢弃最新 `commit`、回退版本、漏掉结算或改变动作发送顺序。
- 断线、重连、快速 AI 连续出牌、技能撤回、结算动画都能恢复到最新服务端快照。

### 设计方案

#### 1. 先绘制骨架，再连接

`DdzView` 首次挂载只渲染固定布局和当前缓存的轻量状态：标题、底分、座位占位、连接提示和操作占位。`ddz_connect`、状态查询和资源初始化在首次 commit 后异步启动。App 已经拿到的 `ddz_status` 通过 props/context 复用，取消 `DdzView` 的重复请求；定时刷新只在状态过期时做。已有牌局从 hook 缓存的最后一份快照恢复，避免切换页面再回到空白桌面。

连接错误只更新连接提示和重试按钮，不让错误状态重建整张牌桌。连接尚未打开时，底分选择、规则查看、离开等不依赖服务端的操作仍可用；需要服务器确认的动作明确显示“连接中”。

#### 2. WebSocket 快照按帧合并

`useDdz` 增加 `pending` 和 `rafId`：消息到达时先做版本检查，将最新快照放入 `pending`，同一帧只安排一次 `requestAnimationFrame`；帧回调再把最新快照提交给 React。版本检查同时比较“已提交”和“待提交”快照，保证乱序消息不会回退。

```text
WebSocket message
        │
        ├─ 旧 commit → 丢弃
        └─ 最新 commit → pending = snapshot
                              │
                    已有 RAF？ ─┤─ 是：等待
                              └─ 否：安排一次 RAF
                                      │
                               setTable(pending)
```

合帧只合并显示快照；错误、连接状态、动作发送和结算通知仍即时处理。诊断模式记录收到数、提交数和每帧合并数，确认改造确实减少了渲染。

#### 3. 将牌桌拆成稳定区域

把 `TableScene` 拆为以下区域，并用 `React.memo` 和明确的 slice 比较器隔离更新：

| 区域 | 只依赖的状态 | 更新条件 |
| --- | --- | --- |
| `DdzTopBar` | 房间号、底分、倍数、连接状态 | 顶部字段变化 |
| `DdzSeat` | 单个座位信息、当前回合、倒计时秒数 | 该座位或轮次变化 |
| `DdzMoveArea` | 三个座位最近公开操作、当前待压牌 | `moves/last/trick` 变化 |
| `DdzHand` | 我的手牌、选中牌、可出牌提示 | 手牌或选择变化 |
| `DdzActionBar` | 当前阶段、可用动作、提交中状态 | 阶段或动作确认变化 |
| `DdzResult` | 结算结果和动画进度 | 进入结算或结算步骤变化 |

子组件不再接收完整 `table`，而接收稳定的 primitive 或小对象。牌组计算（`byHand`、提示和牌型判断）在选择变化或快照变化时执行一次，不能在每个头像和每个按钮中重复执行。

#### 4. 只保留一个活动倒计时

移除三个 `Avatar` 各自创建的 250ms 定时器，改为 `TableScene` 中的一个 `useTurnClock`：

- 没有 `bid/play` 活动回合时不创建定时器。
- 环形进度交给 CSS 动画，React 每 1000ms 只更新一次秒数文本。
- 只把 `turn` 座位的 `secondsLeft` 传给一个 `DdzSeat`，其他两个座位不重渲染。
- 截止时间来自服务端 `deadline`；客户端时间只用于显示，不能用于自动出牌。

#### 5. 特效默认走性能模式

牌局默认使用 `standard` 质量：保留出牌横幅、回合高亮和轻量 CSS 反馈，关闭常驻粒子、炸弹/火箭粒子和大面积滤镜；`prefers-reduced-motion` 强制使用同一模式。`high` 模式才启用现有 Canvas 粒子，且限制同一时间只有一个 effect 实例。

建议在桌面端设置中提供“斗地主画面质量：流畅 / 高质量”，并在牌桌右上角给出当前模式。性能开关只改变绘制，不改变规则、快照或动作协议。后续如需远程止损，可在 `DdzStatus` 增加服务端 `ddz_performance_mode` / kill switch。

CSS 增加 `.ddz-performance`：使用不透明底色、减少阴影和 `backdrop-filter`，禁用太阳纹和非必要渐变；不删除原主题样式，方便回滚。

### 性能诊断指标

开发和内部灰度账号打开 `?ddzPerf=1` 或设置开关后采集本地指标，不上传手牌、用户名和 API Key。每次进入至少记录四个时间点：`t0=view intent`、`t1=首次 React/DOM paint`、`t2=WebSocket open`、`t3=首个牌桌快照`；报告中分开展示网络、Rust attach 和渲染，不用一个端到端数字掩盖慢点：

| 指标 | 说明 | 初始门槛 |
| --- | --- | --- |
| `ddz_first_paint_ms` | `t0` 到骨架绘制 | 常规设备 p95 ≤ 500ms；本地缓存/无网络资源 p95 ≤ 200ms |
| `ddz_socket_open_ms` | 进入视图到 WebSocket open | 记录分布，不作为 UI 阻塞条件 |
| `ddz_first_action_ready_ms` | 首次可操作状态出现 | p95 ≤ 1000ms；慢网另验 `t3 ≤ 2s`，超时不阻塞骨架 |
| `ddz_snapshot_received/applied` | 收到与实际提交的快照数 | 应明显低于当前每条提交 |
| `ddz_render_count` | 一局牌桌 React 提交次数 | 与快照频率脱钩，稳定对局不持续增长 |
| `ddz_fps` | 牌局 30 秒窗口帧率 | 中位数 ≥ 55，p95 不低于 45 |
| `ddz_action_feedback_ms` | 点击到本地反馈 | p95 ≤ 100ms |
| `ddz_long_task_ms` | 主线程长任务 | 单次不超过 50ms，记录异常样本 |

### P0 实施顺序和文件边界

1. `src/useDdz.ts`：加快照合帧、版本保护、开发指标；先不改 relay 协议。
2. `src/components/DdzView.tsx`：拆区域、单倒计时、动作反馈；保留现有公开信息和结算语义。
3. `src/components/fx.ts`、`src/index.css`：质量档位、粒子上限、性能样式。
4. `src/api.ts`/Tauri command：如需远程 kill switch，再增加 `DdzStatus` 字段；默认值必须兼容旧 relay。
5. 本地 Tauri 实机压测后再做 10% 内部灰度，最后扩大到全量。

### P0 验收矩阵

| 场景 | 验收 |
| --- | --- |
| 首次进入大厅 | 常规设备 p95 ≤ 500ms、本地缓存 p95 ≤ 200ms 出现可交互骨架；连接提示不遮挡主要入口 |
| 快速匹配/建房/加入 | 状态连续，按钮不会重复提交；连接失败可重试 |
| 连续 AI 出牌 | FPS 和主线程长任务达到门槛；每一手牌都显示 |
| 炸弹/火箭 | 流畅模式无粒子卡顿；高质量模式只影响视觉，动作仍即时 |
| 倒计时 | 只有当前回合变化；秒数与服务端 deadline 一致，不自动替服务端出牌 |
| 断线重连/乱序快照 | 只接受新 commit；牌局、回合、待压牌和结算不回退 |
| 结算/再来一局 | 结算金额和服务费字段不变；动画结束后按钮可用 |
| 低性能设备/减少动画 | 自动或手动进入流畅模式，不出现白屏和不可点击状态 |

## P1：用户端使用记录

### 页面结构

当前“用量”页保留聚合概览，顶部增加两个标签：

```text
用量
┌──────────────┬──────────────┐
│ 概览（当前） │ 请求记录     │
└──────────────┴──────────────┘
  时间范围  API Key  模型  请求类型       [筛选] [刷新]
  请求数     Token    花费    平均耗时
  ─────────────────────────────────────────
  时间 | 模型 | 类型 | 输入/输出 | 花费 | 耗时 | 状态
```

请求记录默认按 `created_at desc, id desc` 稳定排序，分页每页 50 条；不把全部历史一次性拉入桌面端。点击行打开详情弹窗，展示请求 ID、请求/上游模型、API Key、Token 明细、费用、耗时和状态。

筛选项：日期范围、API Key、请求模型和请求类型。筛选变更使用 generation 号丢弃旧响应，和现有 `UsageView` 的加载方式一致。空状态、加载状态、错误状态和“清除筛选”都要有明确文案。

### 数据和权限

桌面端新增 Rust/API wrapper，映射 relay 已有接口：

- `GET /api/v1/usage`：当前用户的请求级记录，支持日期、模型、API Key、请求类型和分页筛选。
- 记录行详情目前直接使用列表返回的脱敏字段；如后续需要更深的详情，再接入 `GET /api/v1/usage/:id` 并由服务端复核归属。
- `GET /api/v1/usage/stats`、`/usage/dashboard/*`：继续提供概览、趋势和模型汇总。

用户端不使用管理员接口，也不展示上游凭据、完整 API Key 或其他用户信息。API Key 只显示名称和末四位；费用和 Token 以 relay 返回值为准，不在客户端重新计算。

如果产品还要展示斗地主的“对局记录”，应另做“斗地主记录”标签，字段使用 `game_id、开始/结束时间、底分、身份、输赢、净变动、服务费、结果`，数据来自 `ddz_games/ddz_game_seats` 或专用只读接口。它和本节的 API 请求记录分开分页、分开权限和统计，不能把对局金额冒充 API 花费。

## P1：管理员使用记录和用户详情

### 管理员入口

管理员导航增加“使用记录”，与“概览 / 用户 / 抽奖 / 斗地主”同级。管理员记录表默认按时间倒序，列为：用户、时间、请求模型、API Key（脱敏）、上游模型、请求类型、输入/输出 Token、费用、耗时、状态。支持按用户、日期、模型和请求类型筛选；点击一行复用用户端详情弹窗，但增加用户 ID、来源节点和审计字段（仅后端允许返回的字段）。

管理员页面只在打开时加载，手动刷新为主；可选 30 秒刷新，避免记录页持续占用 relay。分页和排序必须由服务端完成，防止大用户量时桌面端排序卡顿。

### 用户详情侧栏

从用户列表点击整行或“详情”按钮打开侧栏，不改变当前列表筛选：

```text
┌ 用户列表 ─────────────────────┬─ 用户详情 ──────────────┐
│ 用户 | 当前并发 | 上限 | 今日 | 状态 │ Ethan@example.com      │
│ ...                           │ 余额       $…           │
│                               │ 并发       3 / 8        │
│                               │ 近 7 天用量趋势         │
│                               │ 最近请求记录           │
│                               │ [查看全部记录] [关闭]  │
└───────────────────────────────┴─────────────────────────┘
```

详情首屏展示余额、状态、当前并发/上限、队列数和最近 20 条记录。余额调整、并发调整历史若当前 relay 没有对应查询接口，先显示“暂未提供历史”，不要用客户端操作日志拼接伪历史；实现阶段补审计接口后再开放该区块。

数据来源：

- `GET /api/v1/admin/usage?user_id=...`：管理员筛选后的请求记录。
- `GET /api/v1/admin/users/:id`：用户身份、余额、状态和限制；当前 candidate 的 `/usage` 关联接口只返回占位统计，不能直接当作详情数据源。
- `GET /api/v1/admin/usage?user_id=...`：用户详情中的趋势和最近记录，必要时由后端增加专用的聚合参数/endpoint，避免桌面端拼接大量记录。
- 现有管理员用户接口返回的 `current_concurrency`、`concurrency`、余额、状态和活跃时间。

## P1：管理员用户列表和并发

### 列表行为

用户列表新增“当前并发”列，显示 `当前 / 上限` 和细进度条；有排队请求时显示队列徽标。默认排序由服务端承担：

```text
sort_by=current_concurrency&sort_order=desc
```

同并发数时按 `last_active_at desc`，再按 `id desc` 稳定排序。点击列标题可切换升/降序；刷新和翻页保留排序与搜索条件。不要只在当前页前端排序，否则跨页结果会误导管理员。当前后端用户列表的数据库白名单还没有 `current_concurrency`，并且实时并发只填充当前页，因此需要先补服务端排序/分页；仅在 React 里排序不能满足这个需求。

列表打开后每 10 秒刷新一次，顶部显示“更新时间”和手动刷新按钮。刷新期间保留旧数据并显示轻量状态，不让表格闪成空白；详情侧栏打开时只更新对应用户行，避免整个侧栏跳动。

### 并发接口和语义

实时值优先来自 `GET /api/v1/admin/ops/user-concurrency`，用户列表的 `current_concurrency` 作为首屏回退。该接口目前只返回有活动并发或排队的用户，并受监控开关影响；缺少的用户不能直接解释成网络错误或假定实时为 0。客户端需要明确区分：

- `current`：当前已占用的并发槽位；
- `limit`：用户允许的最大并发；
- `queued`：等待中的请求数；
- `as_of`：服务端采样时间；监控关闭时显示“实时监控未启用”。

并发值为 null 或暂时不可用时显示“—”，不要把网络错误当成 0。上限按 relay 的限制语义显示；若 relay 以 0 表示不限，UI 显示“当前 / 不限”，实现时在 API adapter 做一次统一转换。

颜色只表达容量风险：低于 70% 为正常，70–90% 为提醒，超过 90% 或有队列为警告；颜色之外同时显示数字和文字，保证色觉可用。

### 用户行交互

- 点击行或“详情”按钮打开侧栏；加、减余额、禁用等现有操作保留在独立按钮，避免误触详情。
- 行和按钮支持键盘焦点、Enter/Space，侧栏支持 Esc 关闭和焦点回收。
- 详情加载失败时保留列表，侧栏显示可重试错误；权限错误不能泄露用户是否存在。
- 自动刷新不抢焦点、不关闭侧栏、不重置滚动位置。

## 回滚和风险控制

- P0 先发布合帧和指标，再打开 `standard` 性能模式；保留 `legacy` 渲染开关，出现回合错乱可立即切回旧渲染路径。
- 质量档位只控制视觉，不改变服务端牌局和动作协议；任何快照版本错误都按严重故障处理。
- P1 页面独立挂载，接口失败只影响对应页面，不阻塞登录、主任务或斗地主。
- 管理员并发自动刷新必须可关闭；如果实时接口超时，显示上次更新时间和“数据可能已过期”，不能展示假实时值。
- 发布前保留当前桌面端安装包和 relay 版本；先停新功能开关，再回退客户端。斗地主在途牌局按服务端状态完成，不能因为客户端回滚而重复结算。
